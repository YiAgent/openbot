Phase 1 — Webhook 接收与入队（FastAPI 同步，立即返回 202）
🐙 GitHub 仓库事件
事件触发对应功能的 Webhook
  • — issue.opened / edited / reopened / labeled → TRIAGE
  • — pull_request.opened / synchronize / reopened → REVIEW
  • — issue.assigned（assignee.type == "Bot"）→ FIX
  • — issue_comment / pr_review_comment（@openbot 开头）→ CHAT
POST /webhook/github · HMAC-SHA256 签名
⚡ FastAPI Route · github_webhook.py
HTTP 胶水层——只做解析，所有业务逻辑在用例中
  • ① 读取原始 body bytes（HMAC 计算需要原始字节）
  • ② verify_signature 常数时间 HMAC 校验 HMAC
  • ③ parse_event → UnifiedEvent（领域对象）
  • ④ 调用 ingest_webhook 用例
  • ⑤ 若 BackgroundTask 回退路径，schedule decide_and_enqueue
  • ⑥ 返回 202（防 GitHub 超时重试）
🔀 ingest_webhook（use_cases/ingest_webhook.py）
主编排逻辑 — 5 个顺序步骤
  • S1 Dedup 去重：Redis SET NX delivery_id，重复 → 丢弃 Redis
  • S2 dispatch_for()：EventKind → Feature；bot 事件过滤（防回声环）纯函数
  • S3 状态机分类：runs_repo.transition() 在资源锁下 CAS 写 task_runs 资源锁Postgres
  • S4 创建 GitHub Check Run（PR 事件立即可见状态）GitHub API
  • S5 入队：XADD v2 QueuePayload；失败 → BackgroundTask 回退 Redis Stream
📦 UnifiedEvent — 领域核心对象
所有 ChannelAdapter 规范化为统一结构，防止 raw payload 直接进 LLM
  • — channel · delivery_id · kind (EventKind)
  • — repo · actor · actor_type · installation_id
  • — issue_number · pr_number · comment_body
  • — event_seq（单调时间戳，用于 late-webhook 检测）
  • — resource_key = github:{repo}:issue:{n} | pr:{n}
  • — raw（原始 payload，只传给需要详情的工具）
⚙️ 状态机 · runs_repo.transition() Intent
在 resource_lock 下 CAS 写 task_runs，防止竞态双 START
START 首次处理此资源，开始新 run
SUPERSEDE 新 push 覆盖旧 review，取消前 run_id
CANCEL issue/PR 关闭，发信号给前一 run
IGNORE event_seq 落后（晚到 webhook），直接 202
取消信号：receive side + worker side 双重发送，防队列延迟漏信号
📬 S5 入队路径分叉
  • ✓ Redis 可用：XADD v2 QueuePayload → entry_id → 202 Redis
  • ↓ Redis 不可用：background_dispatch → route.add_task() → decide_and_enqueue BG Task
两条路径最终都执行相同的 preflight chain + handler 逻辑
Phase 2 — Webhook 异步段（decide_and_enqueue · BackgroundTask 或 Worker 读 v1/v2）
🎯 decide_and_enqueue（dispatcher/decide.py）
运行完整 preflight 链 + LLM 分类器 + 构建 TaskSpec v3
  • ① 加载 EffectiveConfig（读取 .openbot/config.yaml）GitHub API
  • ② 构建 PreflightContext（不可变快照，冻结 dataclass）
  • ③ 运行 10 个 Preflight 中间件链 → 见右侧详情
  • ④ extract_event_context（纯函数，提取分类用 body）
  • ⑤ Direct Actions 检查（规则短路：reply + label，跳过 LLM 和入队）
  • ⑥ LLM 分类器（非 FIX）— 产出 classifier_result + stages_to_run LLM
  • ⑦ DiffScope（REVIEW）— fetch last_reviewed_sha，判断增量/全量/force_push Postgres
  • ⑧ 构建 TaskSpec v3 → XADD 到 Redis Stream Redis
XADD TaskSpec v3 → openbot:workflows Stream
🔴 Redis Stream · openbot:workflows
持久化队列 — 进程重启 Worker 可续跑
  • — v2 QueuePayload（ingest_webhook 写入，legacy 路径）
  • — v3 TaskSpec（decide_and_enqueue 写入，当前主路径）
  • — Consumer Group：openbot-workers，XACK 确认消费
  • — DLQ：openbot:workflows:dead（超 3 次移入）
🛡️ Preflight 中间件链（10 个，顺序执行，首个 BLOCKED 即短路）
最廉价在前，硬门控居中，审计日志在最后
1 SanitizeInputsMiddleware 字节级入口清洗，下游中间件见到净化后的事件 BLOCK
2 KillSwitchMiddleware 环境变量管理员开关，静默所有下游 BLOCK
3 FeatureToggleMiddleware .openbot/config.yaml features.{x}=false 用户可控开关 BLOCK
4 CancelLabelMiddleware 检查 cancel-openbot 标签（1 次 GitHub API，结果缓存 ctx.cache） BLOCK
5 CancelCommentMiddleware 正则匹配 stop/cancel/停 等，§9.4 always-reply，无去重 TTL BLOCK
6 ForkPRGateMiddleware PRD §4.8 安全硬门控，外部 fork PR 不运行工作流 BLOCK
7 ActorRoleMiddleware FIX/CHAT 的 per-feature 角色允许名单 BLOCK
8 RateLimitMiddleware Chat 功能每天/每小时 Redis 计数器，announce_once 去重回复 BLOCK
9 BudgetMiddleware Postgres cost_meter 表累计消费检查 BLOCK
10 AuditStartMiddleware 预检通过后写 STARTED 审计行 — import error 也有通过记录 AUDIT
BLOCKED 路径：write audit_log → announce_once(Redis NX去重) → 可选 GitHub 评论回复
⚡ Direct Actions — 规则引擎短路
分类器调用前的轻量规则，命中则直接 reply + label，不入队
  • — RULES_BY_FEATURE[feature](event_ctx) → DirectAction?
  • — 命中：并发执行 reply() + add_label() → 返回，跳过 LLM 和 XADD
  • — 场景示例：机器人专属标签的 issue 立即确认回复
Phase 3 — Worker 消费者循环（consume_loop · infrastructure/queue/worker.py）
⚙️ consume_loop · 单进程异步消费
两阶段循环：先 reclaim 孤立条目，再读取新条目
  • ① XAUTOCLAIM：领取空闲 >60s 的 PEL 条目（dead consumer 恢复）Redis
  • ② XREADGROUP：读取新条目（block 5s，8 条/批）Redis
  • ③ 更新 queue_depth Prometheus gauge（XLEN O(1)）
  • ④ 对每个 entry 调用 _process_entry
🔍 _process_entry · 版本路由
peek spec_version，路由到对应执行路径
  • v3 TaskSpec v3 → _execute_task_spec → W1~W5 → execute_handler（无 preflight）当前主路径
  • v1/2 QueuePayload → run_dispatch（含完整 preflight 链）兼容路径
v3 主路径
🚀 _execute_task_spec · W1–W5 阶段
W1 Cancel 快检 initial_labels 含 cancel-openbot → XACK + 直接返回，不调 handler
W2 重建 UnifiedEvent spec.to_event() — 从序列化字段还原领域对象
W3 重推 Dispatch dispatch_for(event) 纯函数；upgrade_dispatch 注入状态机字段
W4 加载 EffectiveConfig load_for_repo(adapter, event) — 读取 .openbot/config.yaml
W5 execute_handler 无 preflight（已在 decide_and_enqueue 中执行）→ dispatch.handler(ctx)
✅ 完成处理
  • — REVIEW 场景：store_reviewed_sha 到 DB（供后续增量检测）Postgres
  • — XACK 确认消费 → 移出 PEL
  • — cancellation_deregister(active_run_id)
🔄 重试策略（PEL-based，最多 3 次）
失败不 XACK，留在 PEL 等待 XAUTOCLAIM 重新领取
🔄 Redis 原子计数器 openbot:workflows:retries:{entry_id}（7天 TTL） ≤ 3 次
  • — 第 1~2 次：不 XACK，等 XAUTOCLAIM 60s 后重新领取
  • — 第 3 次：XADD 到 DLQ + XACK 移出主 Stream
⚰️ DLQ：openbot:workflows:dead — 附原始 JSON 供 ops 排查
🚦 跨 Dyno 取消机制
新 push 到来时，保证旧 review 任务能及时停止
  • — Receive side：SUPERSEDE/CANCEL 立即 signal 旧 run_id Redis
  • — Worker side：dequeue 时再次 signal（belt + suspenders）
  • — 当前 run 注册到 cancellation_register(run_id)，被 signal 后 cancel()
  • — CANCEL intent：只 signal 旧 run，自身 XACK 后不调 handler
📊 TaskSpec v3 关键字段
  • — spec_version=3 · scenario · task_id · delivery_id
  • — repo · actor · kind · raw（原始 payload）
  • — intent · run_id · prev_run_id · event_seq · resource_key
  • — check_run_id · initial_labels · classifier_output
  • — stages_to_run · is_incremental · is_force_push

🚧 路线图：自动打标签 · 优先级判断 · Sandbox Issue 复现
🔬 REVIEW maybe_run_review
  • 🎯触发：PR opened / synchronize / reopened / labeled
  • 🤖DeepAgentsReviewResponder：get_pr_diff → LLM 结构化分析 → ReviewFindings
  • 🔽filter_findings 按 config.severity_threshold 过滤
  • 📐分区：inline（有 line）→ 行内注释；repo-wide → review body
  • 🔧DiffScope：增量 / 全量 / force_push 不同处理策略
  • 📋create_pr_review：无 finding → APPROVE；有 → COMMENT（永不 REQUEST_CHANGES）
  • ⚠️Agent 失败 → 发布错误模板 COMMENT，PR 作者可见
🔧 FIX maybe_run_fix
  • 🎯触发：issue.assigned（assignee.type == "Bot"）
  • 📋get_issue：获取 body、clone_url、base_sha、default_branch
  • 🔑get_installation_token：获取临时 GitHub 安装令牌
  • 📦打开 Sandbox：ctx.sandbox_factory() → DaytonaSandboxAdapter
  • 🐙sandbox.clone：token 注入 HTTPS URL，克隆到 Daytona 云端
  • 🤖DeepAgentsFixResponder：Agent 在 sandbox 内执行修复 → FixOutcome
  • ✅tests_passed：create_branch → commit_and_push → open_pull_request → 评论 PR URL
  • ❌tests_failed：评论截断的测试输出（≤4000 chars）
sandbox 未配置 get_issue 失败 clone 失败 agent 失败 push 失败 open_pr 失败

  • 🔍parse_chat_command 解析意图
  • 🚫is_cancel：由 CancelCommentMiddleware 提前拦截，此处防御性 no-op
  • ❓is_help（help / ? / 帮助）：返回固定帮助模板，不调 LLM
  • 🤖freeform：DeepAgentsChatResponder.reply_for_event() — LLM 自由回复

横切关注点 — 审计生命周期 & 可观测性
📝 audit_lifecycle · 工作流审计
所有工作流处理器共用的 async context manager
  • ① 进入：写 STARTED 行（phase, delivery_id, repo, actor, workflow）
  • ② 正常退出：写 COMPLETED + outcome 字段
  • ③ 异常退出：写 FAILED + exception 类型
backend：优先 AuditLogPort → fallback session_factory → 无 DB 时 no-op
🔍 GitHub Check Run 生命周期
PR 事件全程可见处理状态
  • ① ingest_webhook：create_check_run "Starting Analysis..."（同步）
  • ② preflight BLOCKED → update_check_run(skipped)
  • ③ handler 成功 → update_check_run(success)
  • ④ handler 失败 → update_check_run(failure)
  • ⑤ 配置加载失败 → update_check_run "Config Load Failed"
📈 可观测性栈
LangSmith 追踪 + Prometheus 指标 + Sentry 错误追踪
  • — @traceable(run_type="chain") 装饰所有工作流 handlerLangSmith
  • — queue_depth Prometheus gauge（每次消费后 XLEN 更新）
  • — Sentry tag per-dispatch scope：delivery_id · feature · repo
  • — 结构化日志：JSON 格式，extra dict 含完整上下文
