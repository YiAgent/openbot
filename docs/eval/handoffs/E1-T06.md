## Design decision

Original PRD §4.1 calls for `openbot.workflows.review.run(...)` as the future production review workflow. That module is not available yet. Rather than block eval development, E1 establishes a supported **`deepagents_baseline` provider** with the same input/output contract, so:

- We can run the Martian smoke baseline NOW (E1-T08 unblocked).
- E1-T08 / E1-T09 unblock automatically.
- When `openbot_prod` lands, it should be added as a second provider on the same task surface rather than replacing this baseline. The same dataset, scorer, and reporting path are what make the comparison meaningful.

## What was produced

- `evals/solvers/openbot_review.py` — real implementation:
  - `review_diff(diff: str) -> list[Finding]` — pure function that runs a [deepagents](https://github.com/langchain-ai/deepagents) `create_deep_agent(...)` against the diff with a strict JSON-output system prompt, then parses + normalizes findings to `{file, line, body, severity}`. No tools given to the agent (review is closed-form on the diff text).
  - `_extract_json_object()` + `_coerce_findings()` — defensive parsing for when the LLM prepends prose / drifts from schema.
  - `openbot_review_solver()` — Inspect AI `@solver` shim that calls `review_diff` and writes findings into `state.metadata["candidate_findings"]` for the scorer to read.
- Model selection via env: `OPENBOT_REVIEW_MODEL_ID` overrides the default (`anthropic:claude-opus-4-7`). v0.1 dev uses `anthropic:glm-5.1` via the GLM Anthropic-compatible endpoint (`ANTHROPIC_BASE_URL=https://open.bigmodel.cn/api/anthropic`) since an Anthropic key wasn't on hand.
- `pyproject.toml` / `uv.lock` — `deepagents` direct dep added (pulls in langchain + langgraph + langchain-anthropic).

## Decisions made

- **`deepagents_baseline` as a durable comparator** — Why: future evals should show where OpenBot itself beats a credible off-the-shelf agent path, not just whether it clears an absolute score. Keeping both providers on one harness gives apples-to-apples comparisons across quality, latency, and cost. Follow-up: add `openbot_prod` as a second provider when the production workflow exists; do not delete this baseline.
- **`OPENBOT_REVIEW_MODEL_ID` env override** — Why: PRD §17 #5 locks `claude-opus-4-7` for production gates, but v0.1 dev needs flexibility (GLM today, opus tomorrow, weekly Haiku for cheap regressions). Env override lets the same code path drive baselines across model variants. Production gate scripts must always set the env to the locked model. Follow-up: E2/E3 cron workflow sets `OPENBOT_REVIEW_MODEL_ID=anthropic:claude-opus-4-7` explicitly to satisfy the PRD §17 #5 lock.
- **No tools given to the agent (`tools=[]`)** — Why: at this stage the review is closed-form on the diff text — no shell, no fs, no sub-agents needed. Adding tools changes the latency / cost profile and the failure modes. Will revisit when the production workflow needs to consult docs / git blame / etc. Follow-up: the production workflow will likely give the agent `read_file` over the patched files for context — that's a `openbot.workflows.review` design decision, not an eval one.
- **Defensive JSON extraction (`_extract_json_object`)** rather than strict structured output — Why: the JSON-only system prompt works most of the time, but LLMs occasionally prepend prose. Regex-based last-balanced-`{...}` extraction is more robust than `response_format=` with a schema (which sometimes silently coerces). Follow-up: when langchain-anthropic structured output stabilizes for non-Claude models (GLM via the compat endpoint), revisit.
