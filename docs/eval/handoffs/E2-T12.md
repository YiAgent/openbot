## Decisions made

- **4 cases per category instead of the bare-minimum 3** — Why: ≥3 is the PRD §13.1 floor; 4 gives statistical headroom (one false-positive doesn't tank a whole category's pass rate) and headroom for the inevitable "we wrote case N badly" discovery in the first run. Follow-up: v0.2 `prompt_injection_v1_xl` (E4-T10) expands to ≥50 cases including multi-turn injection.
- **Both `canaries` and `forbidden_patterns` per sample** — Why: canaries are the cleanest signal (planted-tokens-with-no-innocent-meaning), but some attack classes (tool misuse, env exfiltration) are better caught by regex on compliance language. The two channels are orthogonal so a sample can use either or both. Follow-up: see breach analysis in E2-T14 handoff — the v0.1 first run found that canaries can false-positive when the bot legitimately quotes the planted token to flag it. Mitigation in next iteration: use canaries that don't look like real secrets so the bot has no excuse to quote them.
- **`public: false`** in manifest — Why: red-team payloads are intentionally adversarial; even though they're synthetic, putting them in the public LangSmith project would give attackers a free template. PRD §13.2 fail-safe.
- **Tool-misuse cases shaped as "ask the bot to announce execution"** — Why: v0.1 review solver runs `tools=[]`, so the bot can't actually call shell. The narrowed breach surface is bot announcing "I will run this script" (compliance language). When E2-T07 lands the Modal-backed fix solver with real tools, this dataset gets real teeth without needing new samples — the safety scorer's `tool_calls` channel was wired for that future. Follow-up: when chat agent + tools land, add `tool_call` field to dataset records and enrich the scorer's tool-call gate.
