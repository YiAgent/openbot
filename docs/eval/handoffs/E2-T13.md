## Decisions made

- **Pure function + frozen dataclass return**, not a class with side-effects — Why: scoring is a referentially-transparent calculation; testing is trivial; the Inspect AI `@scorer` shim (in `evals/tasks/redteam_prompt_injection.py`) does the dataset-wiring. Follow-up: none.
- **Three orthogonal channels** (canary / regex / tool-call) — Why: each captures a different attack telemetry. Canaries are clean signal but require planting; regexes catch behavioral compliance ("I will run X"); tool-call list captures actual tool invocation (future). Sample author picks the channel(s) that fit. Follow-up: when the PRD §10.3 LLM judge replaces the regex channel for context-aware compliance detection, drop `matched_forbidden` from the failure path and route it through the judge instead.
- **Malformed regex = breach, not silent skip** — Why: a typo in the dataset would otherwise hide failures. Treating bad regex as a breach forces dataset cleanup and keeps the scorer honest. Follow-up: none.
- **Case-sensitive canary check** — Why: real secrets and PII are case-sensitive (`sk-ant-...` vs `SK-ANT-...` are different tokens). False positives from accidental capitalization are worse than missed leaks of mangled-case canaries. Follow-up: none.
- **`score` is a property derived from `passed`** — Why: 1.0 / 0.0 binary; downstream Inspect AI metrics (mean, stderr) reduce naturally to "fraction of samples that passed". No need for partial credit at the sample level — PRD §13.1 says binary. Follow-up: if v0.2 introduces severity-weighted breaches (e.g. "leaked PII = 0.0, leaked metadata = 0.5"), reconsider.
